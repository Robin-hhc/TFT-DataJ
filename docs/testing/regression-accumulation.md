# 历史问题的回归积累机制

历史问题尚不能全部称为完整自动覆盖。本次按实际断言审计了 **24 个历史问题主题**：13 项已有针对具体故障的自动回归，11 项仍是局部覆盖。另登记 `REG-025`，约束台账、测试执行与批准样本不能静默退化。详细范围、限制、历史提交、真实测试方法 ID 和公开/私有运行范围记录在 [regressions.json](regressions.json)。

这里的“自动回归”只对应每项 `verified_scope`，不代表已覆盖所有游戏画面。局部项即使现有测试全部通过，也继续保留 `partial` 和限制，不能按绿色测试总数升级为完整验收。

## 每次发现问题后的闭环

1. **保存原始证据。** 复用故障发生时已有的截图，保存来源目录、版本、阶段、阵容、候选槽位与必要状态。原图和原始记录保持不变。来源统计错误还需冻结实际请求、响应和显示值。
2. **独立核对预期。** 看原图和对应来源后建立绑定图片哈希的 `expected.json`。失败 observation、旧浮层文字、当前代码输出都不能直接成为答案。暂不能独立确认的记录保持 pending，不能算通过。
3. **先复现，再修复。** 为具体故障补会失败的回归；身份、阶段数据、异步发布、显示寿命等按问题所在链路测试。修复后检查该项通过，并保留原图和原先失败证据。
4. **登记永久保护。** 更新 `regressions.json`，填写具体问题、精确测试方法 ID、public/private 范围、证据与限制。可公开的匿名裁图和冻结来源按哈希登记；私有原图只登记批准索引，不公开玩家画面。
5. **统一验收。** 公共 CI 检查已登记的方法确实存在、按登记范围被执行且通过，并核对 fixture。需要私有图片的改动在本机完整入口复验。报告逐项保留未执行、失败、跳过和局部覆盖，不用总数代替结论。

后续修改不能靠删除历史项、移到不执行的私有模块、删除批准原图或放宽预期来恢复绿色。确有必要改变范围时，记录可审阅的原因和证据；统计基准更新也须重新独立核对，不能用修改后代码批量生成正确答案。

## 已批准的私有样本

[private-bug-baseline.json](private-bug-baseline.json) 登记现有 **31 份**已独立核对的病例，每份锁定 `frame.png`、`case.json`、`expected.json` 三个 SHA-256。第 31 份为 2026-10-11 独立核对的“拥抱 I”漏识别原图，旧 30 份及批准哈希全部保留，见[现场验收记录](../development-records/2026-10-11-live-match-conditions.md)。索引不包含图片、玩家上下文或 OCR 内容。完整本机验证要求这些批准文件存在、哈希一致且 oracle 合法；删除 `expected.json` 后不能悄悄退回 pending。

其他已查看但没有完整 oracle 的记录仍另列 pending。身份回放只验证场景、身份、类别和海克斯回合，不证明排名、浮层像素或性能正确。涉及这些问题须补对应来源和界面链路回归。

独立核对并保存新病例的 `expected.json` 后，在仓库根目录登记。例如本机源码归档目录为 `work/companion/bug-cases`：

```powershell
python -X utf8 tools/validate_bug_cases.py --cases-dir work/companion/bug-cases --review-baseline docs/testing/private-bug-baseline.json --register-reviewed-case case-ID
```

将 `case-ID` 换成真实病例目录名；EXE 或其他归档位置通过 `--cases-dir` 指定。登记只追加所选合法病例，不能覆盖旧批准哈希，不从 observation 生成 oracle。登记命令输出注册结果；之后运行完整验收写结构化报告。

## 运行入口

公共检查无需 MuMu 或私人图片。Windows CI 使用相同入口，并执行数据故障注入：

```powershell
python -X utf8 tools/validate_data.py --release-gate --report work/data-validation/offline.json
python -X utf8 tools/check_data_mutations.py
```

本机具备批准原图和 OCR 运行环境时执行完整回归：

```powershell
python -X utf8 tools/validate_data.py --include-private --release-gate --report work/data-validation/with-private.json
```

如归档来自 EXE，给完整入口追加 `--bug-cases-dir` 和实际目录。独立的新归档还须显式给出自己的 `--bug-review-baseline`，报告会标明所用索引；不能借此声称已经验过源码归档的 31 例。开发机可将 `python` 换成 `work\p0-runtime\Scripts\python.exe`。公共 CI 不读取私人原图，其私有样本检查只验证索引结构并明确标记未执行；本机完整入口才校验批准文件和实际原图回放。

报告的 `test_outcomes` 保存实际方法结果，`regressions.cases` 按历史问题列出对应方法、执行范围与限制，`review_baseline` 列出批准文件完整性，`bug_cases` 列出独立原图回放结果。默认源码归档禁止用替代索引减少批准样本；只有显式指定不同归档时才允许独立索引，`project_review_baseline` 仍保留源码索引的未执行范围。公共的 25 份冻结素材绑定 SHA-256，文本统一为 UTF-8/LF 后计算，避免 Windows 换行差异误报；既有素材不能靠更新哈希替换，新的来源或预期使用新文件路径并独立核对。报告不得覆盖登记素材、证据、台账或批准索引，失败报告也遵守此限制。

验证其他归档时，默认源码原图目录仍受保护。先建立项目素材保护，再读取自定义登记文件；输入损坏导致保护无法建立时，只在控制台给出失败诊断，不写可能破坏原始证据的报告。

CI 完整获取 Git 历史，推送时与前一提交、PR 时与目标分支提交比较台账及批准索引。本机默认与已提交 `HEAD` 比较，也可显式传入 `--regression-base-ref 提交SHA`；不可用提交直接失败。历史项不可删除；确需替换测试或降低覆盖范围，须填写本次新的 `coverage_change_note`，旧理由不能反复授权新的保护缺失。该字段是审阅记录，不能自动证明理由充分。

## 仍需补证据的情况

早期“大剑”反馈的独立实图实际是巨人腰带，不能用那张图片证明暴风之剑。2026-10-11 第三局新增了真正暴风之剑主标题原图，先独立冻结 equip / 1001，再核对实际读取、检索请求及成功重试后的 Qt 展示，详见[现场验收记录](../development-records/2026-10-11-live-match-conditions.md)；该现场证据尚未单独加入上述私有自动回放基线，不能把两种覆盖混为一谈。MuMu 合成器中的闪现、真实游戏 FPS、物理鼠标侧键与点击穿透、另一台实体电脑的 EXE 兼容仍需现场或专项采集。自动记为已选缺完整物理选择证据，双行已拥有海克斯列表也尚未纳入当前单详情读取入口。

这些限制已保留在台账中。积累机制保护已确认的失败及验收范围，后续取得新证据后继续追加，不把当前样本集合解释为所有历史问题都已完整解决。
