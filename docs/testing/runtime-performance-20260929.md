本轮针对手动触发卡顿、均排偶发消失和内存占用。对照提交为 `a940d5d2637c2ea4e56933a9435b90a3c2f50d8b`，未改 OCR 模型、排名口径或降低截图文字清晰度。

## 已复现的原因与修改

| 原因 | 修改与验证 |
| --- | --- |
| 手动刷新先调用返回游戏并清空结果；第一次阶段检查也会清掉同阶段的手动结果 | 游戏内刷新保留当前均排，先确认画面是否变化；相同阶段不重置。对应测试修复前失败、修复后通过 |
| 卡片检测、整张4K图归一化及多次文字指纹计算在Qt界面回调里执行 | 图像检测与指纹计算移至后台串行队列；仅采样需要的文字区域，保持原Lanczos网格；多分辨率独立整图参考校验通过 |
| 图像库默认使用本机20个处理线程 | 限制OpenCV为1线程；ONNX原有2线程限制保留；游戏前台侧键省去原有100毫秒面板关闭等待 |
| 已确认选项反复按侧键仍重复OCR | 画面未变化且三项确认完整时复用OCR结果；未确认项、候选变化和失败统计仍可重试 |
| 60秒阶段窗口/30秒手动窗口过期后停止验证，结果因截图过期消失 | 选择画面仍被确认时继续检查；换牌时清旧数据，并为手动/自动重新识别分别保留30/15秒，仍遵守OCR冷却 |
| 棋盘形状被误提名为装备选项，抢占海克斯流程 | 三个海克斯刷新按钮优先于装备形状提名；候选变化先撤销旧排名 |
| 完成的Qt任务、信号回调和任务函数循环引用，持续持有旧截图 | 成功/失败均断开信号，释放任务函数；失效会话释放最后一帧。禁用循环GC的真实Qt弱引用测试两条路径均通过 |
| 同画面复用结果后，失败的阵容查询不能手动恢复 | 单独重试失败统计，保留有效全局行；若全局重试也失败，清除旧值，防止下一帧重新显示 |

## 测量方法

同一台Windows开发机，OCR模型已加载，真实3840×2160截图回放。截图SHA-256为 `d7505218a2d2500688a2ab59bbb73d838a577d4dd997b91bdd2c596e541da4fd`。每次模拟截图分配新的完整图片，统计使用固定快照；实际Qt事件、识别、数据转换和结果更新均运行，原生窗口位置设置替换为记录器。

每组8次手动触发，之后20次截图验证；另做200次连续截图。对照按顺序运行，不并行构建。下表为一次接受的本机结果，不作为跨机器性能保证。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 同组选项反复触发，中位数 | 512.29 ms | 30.20 ms |
| 每次重新识别候选，中位数 | 原流程每次均重复识别，512.29 ms | 232.96 ms |
| Qt 5ms心跳的最大实际间隔 | 173.09 ms | 9.24 ms |
| 文字指纹计算中位数 | 51.86 ms，界面线程 | 1.99 ms，后台线程 |
| 8次触发+20次验证，进程CPU时间 | 7.219 s | 1.266 s；每次重新识别组为4.203 s |
| 验证后主进程工作集 | 591.39 MiB | 326.88 MiB |
| 主进程峰值工作集 | 665.61 MiB | 368.43 MiB |
| 清空会话后工作集 | 591.39 MiB | 295.25 MiB |
| 验证后主进程私有提交量 | 1133.66 MiB | 868.71 MiB |

200次连续截图后工作集从328.78变为329.47 MiB，清空会话降至297.84 MiB；没有观察到随截图数量持续累积。此次约7秒的加速回放不是数小时稳定性测试。工作集与私有提交量含义不同，均不是整台机器总内存。

最初复用同一张图片的回放只显示小幅内存改善；改为每次创建新截图后才暴露回调持有问题。因此默认不应仅凭复用图片的RSS报告判断内存健康。第一版后台化修改在此更强的检查中出现更高峰值，未作为完成结果；回调生命周期修复后重新测量得到上表。
