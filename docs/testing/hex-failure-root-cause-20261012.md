# 2026-10-12：海克斯失败为何反复出现

本轮从 `1ae8f6a6c40cacebebaf0c5b6bbe4afb55be4c42` 的源码、10-11/12 本机日志、最新原图和独立来源请求定位。实际执行及最终验证见[本轮记录](../development-records/2026-10-12-hex-failure-root-cause.md)。原图、原始响应、失败运行和诊断报告留在本机；以下统计不是独立对局成功率。

## 工具与识别链路

TFT-DataJ 是 Windows/PySide6 金铲铲助手。它读取已绑定 MuMu 的截图，识别海克斯、装备及详情标题，再按 DataJ 的实体 ID、版本、获取阶段和固定阵容查询统计，显示全局/阵容均排。它不读取游戏内存。已选资源需要用户明确确认。

实时海克斯路径：自动回合探查或手动侧键 → 截图 → 16:9 布局/三个刷新控件门槛 → 回合与三个标题区域 OCR → 多视图精确目录共识 → 必要时描述消歧 → 像素签名复验 → 全局统计 → 定阵主表 → 同 ID/同阶段精确补查 → 当前 token 下的 Qt 发布。固定阵容预读在后台使用同一来源预算。

“立即补查一次”首先重读当前画面；统计补查只有在身份已确认后才成立。目录没有实体、名称同名但身份无法区分、来源没有该阶段统计、网络/结构校验失败是不同的问题。重复截图无法补齐上游实体目录。

## 当前证据与根因

| 证据 | 可以确认的原因 | 不可以据此推断 |
| --- | --- | --- |
| 两张 10-12 原图的“战时补给：女神之泪”七个可信直接读数一致；归档目录没有精确标题；新取 `/gamedata?setId=18` 的 263 行及 `18.3` 全局 226 行仍没有该项 | 当前来源目录/统计缺项；安全拒识，不是这两例标题裁剪失败 | 不能借其他战时补给的 ID 或按 ID 数列猜答案 |
| “致命丽花”三个标题读数一致；来源两个 ID 的名称/品质/描述相同，图标地址不同；全局只返回一个 ID | 目录同名身份无法靠当前标题/描述安全区分；现有别名投影要求完整等价 | 单个统计有值不能单独授权把两个 ID 合并 |
| 实际 DataJ 的受控 503 后，来源恢复、共享冷却到期，旧预读仍停在失败状态 | 失败处理缺少恢复转移；本局剩余预读永远不再执行 | 历史每次补查失败的原始网络原因未被保留，不能断言全部都是 503 或冷却 |
| 实际 DataJ 接收 HTTP 200、非法阶段数值，之后同 scope 返回正确响应，重试仍命中旧坏缓存 | `_send_request` 先写缓存，海克斯域校验随后拒绝，但主表没有清除坏条目 | 新重试任务不能自行消除尚在 900 秒缓存期内的坏数据 |
| 实际 Companion → DataJ → 部分补查失败，另两项成功；原来没有终态问题归档，异常只剩通用文字 | 局部失败以成功 dict 返回，应用仅归档 `comp_result is None`，遗漏部分失败；原始异常分类丢失 | 不能用日志中的失败 ID 还原已丢失的历史 HTTP 请求异常 |

原始日志截面中：152 次选择页 OCR 完成，102 次三卡确认、40 次两卡、8 次一卡、2 次零卡；这些包含同一画面的重复扫描，不是 152 个独立选择事件。21 个统计发布快照带逐项补查错误，同样包含进度和终态重复。普通页面的 `no_refresh_glyphs` 不应算作选择页漏识别。

当前来源复查还表明：`18.3` / 耐心学习 / 2-1 / 阵容 121 返回 73 局、5.00；兽性本能+ / 4-2 的检索合法但没有阵容 113。前者证明这次来源已恢复，后者属于合法无数据；不能把无数据作为需无限重试的网络错误。

DataJ 元数据 `season=S19` 与请求 `setId=18` 在全部旧批准病例中已经共存。本轮没有独立证据证明它是赛季串用，不把该字符串差异列为已证根因。

## 本轮采纳的修正

1. 标题匹配保留原身份门槛，新增原因：目录无精确标题、可信读数不足、读数冲突、目录同名歧义。目录无匹配仅表示 OCR 共识与当前目录不相容，并不自动证明 OCR 正确。界面不再把此类问题都称为名称待确认。
2. 预读失败不写负缓存；失败 worker 退出后，仅保留一个可取消延迟唤醒，在至少 60 秒并且共享来源冷却到期后恢复。其他请求延长冷却时重新等待；新局、换版本/阵容或退出取消唤醒。历史立即失败/worker 退出测试保留。
3. 海克斯主表域校验失败时仅删除同键、同获取时间的缓存，保护并发写入的新响应。真实合法空结果仍可负缓存。
4. 部分补查的终态错误附带精确请求、scope、异常类型、HTTP 状态/响应哈希和冷却时间；保留全局及其他成功项。进度快照不重复登记终态失败；过期回调不登记当前问题。异常原文、请求头及凭据不进入诊断。
5. 每个补查终态的安全诊断写入本机事件日志。原图保存仍遵守前台、新鲜度、有界队列和去重限制；日志取证与原图是否能再次保存分别记录。

新增保护按原方法 ID 登记到[历史台账](regressions.json)，原有条目、公开 fixture 与批准哈希保留；三份独立核对原图只验证场景/阶段/身份及安全拒绝，不证明缺失实体已经补齐。

## 为什么以前测试通过仍会反复失败

- 旧批准集 31 例全部来自 `18.3`、3840×2160 海克斯场景；5 例三卡确认、24 例两卡确认、1 例全拒绝、1 例 unknown。它保护已知行为与拒绝错误身份，不能代表全标题识别率、其他尺寸或其他版本覆盖。
- 原图回放使用每例归档的目录；它不会发现今天获取目录的缺项，也不验证补查网络、共享冷却及最终显示。
- 冻结显示矩阵的 `source_gaps` 为空只证明该矩阵覆盖完整，不代表在线来源今天没有缺项。
- 原来的八个数据故障注入主要保护版本、统计范围、排序/阈值、槽位和显示；没有直接覆盖目录缺项、来源恢复、坏海克斯主表缓存及部分失败归档。
- 几个 Qt 补查用例把 `bugs.hex_statistics` 整体 mock 掉，验证显示，却无法发现真实归档没有被触发。本轮新增实际 BugReporter/BugCaseStore 临时目录的链路测试。

## 后续守护与边界

每个新失败先保存原图与原始来源范围，再独立核对，按原因补对应 seam 的 red/green；统计错误另留请求/响应与实际 Qt 结果。回归矩阵应同时列出“应成功”和“应安全拒绝”，按版本、标题/品质、阶段、窗口尺度及失败恢复分层，不能用总测试数或批准图数表示识别成功率。

来源完整性需要单独的维护闭环：记录目录/统计获取时间和内容摘要，核对新增未匹配标题，独立确认合法 ID/品质/描述后再纳入目录。如果来源仍缺项，应明确展示缺项并保持未知身份。不能自动从失败 observation、模糊同名或其他阶段排名生成新答案。

本轮离线回放和受控 HTTP 不证明现场 MuMu 合成、物理侧键、游戏 FPS、便携 EXE 或另一台电脑；现存进程不会自动加载修改后的源码。源代码统一验证与这些现场/包验收分别留档。
