# 定阵海克斯排名延迟修复 · 2026-10-09

## 复现与原因

现场 `work/companion/pipeline.jsonl` 中，全局排名显示后，阵容105的4-2组又等6.291秒，2-1组又等4.242秒。旧路径先取全局和阵容主表，再逐项补查最多三个海克斯，每次HTTP完成后再等一秒，最后一次完成后才统一显示。刷新只淘汰回调，旧组仍占查询队列。

两个真实Qt回归先失败：主表已有两项排名却被另一项慢补查阻塞；已完成补查仍等待最后一项。证据在 `work/hex-latency-20261009/red.log`。批次并发及缓存快速返回也通过失败测试或内存变异确认。

## 实现

- 定阵详情完成后，后台预读全局与阵容海克斯主表。
- 海克斯使用独立两线程Qt任务池，缓存直接返回，不等待普通请求的长锁。
- 当前组最多三项独立补查并行，复用一份HTTP客户端；同一适配器包括普通查询在内，最多三个活跃HTTP，相同在途请求共享结果。
- 主表已有排名先显示，补查逐项发布不可变快照，保持原槽位；未完成项继续显示读取中，同组查询完成前不重复排队。
- 保留同版本、ID、阶段、阵容验证，没有合并条件改变统计范围，没有借其他阶段或全局均排填空。
- 排队及开工前检查当前会话，过时任务不继续发送或发布。已发请求可以写精确范围缓存；补查批次读超时四秒、连接超时两秒。
- 普通请求仍在完成后间隔一秒，失败共享六十秒冷却，晚成功不能清除失败冷却；有效缓存仍可读。
