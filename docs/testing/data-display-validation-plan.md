# 数据显示自验证方案

日期：2026-09-28。基线提交：`75d887e`，当前发布程序：v0.2.1。

状态：**T1–T6 已落实；实现、运行方法及验收结果见 [运行说明](README.md) 和 [本轮结果](validation-results-20260929.md)。下文保留批准时的问题、目标和验收约定。**

## 目标与漏检原因

用户看到的实体、阶段、版本、全局/阵容范围、数值、样本、排序和缺失状态都需要被验证。测试的验收对象是最终卡片、表格和浮层，不能停留在“接口返回成功”或“有多少行”。

“黑暗仪式”事件中，接口确实返回了仅1局样本、均排2.00的裁决螳螂；网站另在前端过滤不足50局的阵容。旧测试检查请求条件和原始行数，没有检查最终可见结果。v0.2.1补上了这个单例，但尚未形成覆盖其他页面的数据验证体系。

代码盘点发现：

| 现有检查 | 能证明的范围 | 缺口 |
| --- | --- | --- |
| `test_dataj.py` 7项 | 请求参数、部分结构和缓存隔离 | 多数返回空表，不能证明结果顺序或界面数值正确 |
| `test_comp_browser.py` 3项 | 黑暗仪式真实响应回归、49/50边界、缓存和排序 | 只有一个真实条件；没有覆盖所有条件种类、百分比和更多版本 |
| `test_item_stats.py` / `test_item_values.py` 7项 | 装备作用范围、非法字段、阵容缺项补查、持有者过滤 | 尚缺成套的真实数据到最终浮层文字对照 |
| `test_stat_colors.py` 1项 | 3个颜色值 | 尚缺格式边界与不同显示位置的颜色一致性 |
| `integration_check.py` | 固定阵容、部分阶段值、页面流程 | 英雄出装主要检查103行及首行颜色，未检查这些行是否应该展示 |
| `check_item_flow.py` | 装备流程、过期响应、稳定帧 | 持有者为合成样例，并替换了绘制入口；不能据此证明最终头像、文字和列归属正确 |
| `outputs/mumu-p0-probe/test_snapshot_stats.py` 3项 | 阶段取值、缺阶段不退回总值、阶段编号冲突 | 不在常用 `unittest discover -s outputs/companion` 的59项中 |

静态盘点为 companion 59个测试方法、mumu-p0-probe 14个；这不是本轮重新运行全部73项的通过声明。部分真实图测试依赖未提交的 `work/` 文件，缺失时会跳过。核心数据回归必须能从干净克隆独立运行。

## 首轮抽查已发现的问题

本轮获取目录、全局/阵容强化、全局/阵容装备、阵容英雄出装共6份响应，形成14组观察；其中2组通过真实隐藏界面进行对照并发现差异。其他12组是取值与范围抽查，不等同于与网站页面全面对账。

**新增确认缺陷：英雄出装的单件和三件套未应用网站默认50局门槛。**

条件为 S18 / 18.2a / 地狱火95（112）/ 阿木木（4503）/ 全部装备 / 均排升序。使用同一份最新响应，网站规则独立筛选后与实际助手表格比较：

| 页面 | 助手当前首项 | 按网站默认门槛后的首项 |
| --- | --- | --- |
| 单件 | 光明版生命药水，1.00，3局 | 护卫纹章，3.15，920局 |
| 三件套 | 冕卫/狂徒铠甲/护卫纹章，2.17，29局 | 圣盾使的誓约/棘刺背心/薄暮法袍，2.61，69局；存在同均排项 |

单件接口109行，50局门槛后40行；三件套200行，门槛后111行。数值为本次快照，不是永久排名或出装建议。并列均排不应在没有次排序约定时强制唯一先后。

证据：当前[阵容页面](https://www.dataj.cc/comp/112)引用的[前端组件](https://www.dataj.cc/_next/static/chunks/0969vttc_sol9.js)将英雄出装最小样本初始化为50，并在 `heroEquips` / `hero3Equips` 展示前过滤。助手 `app.py::query_equipment` 目前只有类别筛选与排序。批准计划时实际控件已复现差异；本轮已通过先失败、后修复的真实控件回归修复。

本地证据保留在 `work/data-display-audit/`：`initial-audit.json`、原始响应、前端源码、两张实际界面截图。结果文件SHA-256为 `d932de6cede056627505dcab052cd3cbea1bfe2f7f512a2953308aa1b703f264`。发布前应将精简且去除私人内容的数据样例纳入仓库，不能依赖这个工作目录。

## 用户场景与验收目标

1. 作为玩家，我希望检索一个条件后看到有足够样本的阵容，以免被偶然的第一名误导。
2. 作为玩家，我希望三个阶段显示各自的海克斯数据，以免把总均排或其他阶段当成当前阶段。
3. 作为玩家，我希望全局与本阵容数值各有明确来源，以免把全局数据当成定阵数据。
4. 作为玩家，我希望成装、神器和光明装备保持各自身份，以免相似名称对应错装备。
5. 作为玩家，我希望持有英雄的名字、头像、均排与样本对应同一英雄，以免看到错位或同名串数据。
6. 作为玩家，我希望单件和三件套出装都按明确样本门槛筛选，以免低样本结果排到前面。
7. 作为玩家，我希望切换阶段、阵容、版本或候选后撤下旧结果，以免迟到响应覆盖新选择。
8. 作为玩家，我希望“无数据、读取中、查询失败、未识别、未定阵”能区分，以免空值看起来像低均排或零。
9. 作为玩家，我希望断网、缓存命中和重启都维持正确口径，以免缓存中混入其他局或版本的数据。
10. 作为使用便携版的玩家，我希望已下载EXE执行与源码相同的数据规则，以免源码修了而发布包没修。

## 三层校验

### 1. 数据规则单元测试

使用小型、明确标注为合成的数据，检查边界和不变量：

- 样本0、1、49、50、51；缺失、负数、布尔值、字符串样本；不能简单转换后当成有效数据。
- 均排1与8，以及越界、空值、NaN、Infinity；百分比0、100、越界；异常响应不得展示可信数值。
- ID为整数/字符串、重复ID、同名不同品质、普通与光明同名词根；按身份匹配，名称或头像相同不代表实体相同。
- 阶段索引与标签一致；缺少当前阶段时不回退全阶段；缺阵容统计不拿全局填充。
- 过滤在排序和分页之前；输入顺序不改变排序结果；均排并列按界面约定验证，不凭名字硬排。
- 百分比单位、保留小数、千/万样本缩写和颜色边界；预期值从页面规则或人工核对的固定值产生，不调用被测格式化函数生成答案。

**阈值按功能分别定义，不能把“50局”机械套到所有数值上：**

| 显示位置 | 目标规则 |
| --- | --- |
| 阵容推荐、英雄单件/三件套排行榜 | 默认先过滤不足50局，再排序 |
| 装备浮层的持有英雄 | 过滤不足50局；固定阵容时还必须属于攻略英雄ID集合 |
| 装备浮层的候选均排 | 小样本仍可显示，但明确标“少”，不能冒充高置信度推荐 |
| 当前三个海克斯的阶段均排 | 保留已有候选对比行为；验证真实样本和阶段，不能因榜单门槛而擅自抹掉已选候选的数据。低样本提示作为明确展示规则单独落实 |

### 2. 真实快照到最终显示的回归

保留真实 DataJ 响应，测试仅替换网络传输和可控时钟。执行实际适配器、页面事件、筛选排序及卡片/表格/浮层更新，读取最终控件文字、样本、颜色、实体与槽位。不得用伪造的 `render()` 通过显示验收。

使用现有 `CompBrowser.set_result`、`Companion.query_stats`、`Companion.query_equipment`、`ItemController` 与 `ItemOverlay.update_row` 接口，不为测试先做大规模重构。必要时只增加稳定的控件标识或复用小型统计规则。核心数据测试直接输入已确认ID，避免把每次数据测试变成OCR测试。

期望值独立保存，来自同条件的网站显示或已核实的网站规则＋原始响应。禁止调用应用自己的筛选、排序、格式化方法生成“正确答案”。

除了前5名，还核对整个结果集合、总数、过滤掉的低样本行、空态、末页、并列组；浮层核对每一个槽位，不能将排序后的数值贴到原来的另一张候选卡上。

### 3. 真实网站抽查与发布EXE回放

发布前人工触发抽查，不设置定时任务或后台爬取。网站与助手必须统一赛季、版本、阶段、阵容、实体、类别、最小样本、排序方向。网站默认出场率与助手均排优先不能直接比较名次。

独立采集站点页面显示、实际请求和响应，记录采集时间；有条件时让两边消费同一份冻结响应。只能拿到接口而拿不到页面显示的案例标“接口核对”，不能冒充“页面一致”。

若两次查询发生数据更新，保留两次响应并明确标记待复核，不放宽数值误差让它通过。相同原始响应下：实体、样本和状态必须完全相同；显示小数按约定取舍后完全相同。不同统计接口的聚合口径未核实前不要求样本相等，也不相互替代。

数据请求复用整表，串行且间隔不少于1秒；单批最多20个实际请求，遇到429/拒绝/结构改变立即停止该批并报告。正常提交只跑离线回归。抽查完成后用**最终发布ZIP中的EXE**回放同一批核心样例。

## 第一轮覆盖矩阵

这是实施时的最低覆盖目标，**不是当前已经完成的数量**。每次按目录和可用版本冻结具体ID；两个版本选当前默认和一个网站仍提供的旧版本，三个阵容至少包括112、120、100或当轮有效替代。

| 领域 | 第一轮抽样 | 必查内容 |
| --- | --- | --- |
| 阵容检索 | 普通装备、转职、海克斯、英雄、羁绊各至少4个条件，共20个；另查无条件列表 | 热门/冷门、低样本领先、空结果、不同羁绊档位；两个版本、两种排序，前5与全量集合 |
| 海克斯 | 银/金/彩每类3个，共9个；覆盖三个阶段，全局＋三个阵容，两个版本 | 有/无阶段、同名等级、全局与阵容显著不同、同一ID跨阶段不同；阶段缺项不是0 |
| 装备候选统计 | 成装/神器/光明每类3件，共9件；全局＋三个阵容，两个版本 | 原表有值、阵容缺项补查、两边都缺失；均排和样本不能由持有者平均得到 |
| 装备持有者 | 每种装备类别至少2件，覆盖上述范围 | 前两名英雄ID、头像、数值、样本、范围；攻略之外英雄、同名不同ID、没有达标英雄 |
| 英雄出装 | 三阵容各选主C和前排，共6个英雄；单件/三件套、全部/成装/神器/光明、两个版本 | 第一名、前5、全量集合；三件套“包含该类型”；补充转职/特殊分类各至少一例 |
| 生命周期与失败 | 覆盖每个数据入口，而非仅测试公共会话对象 | 版本A→B→A、阵容A→B、阶段变化、换一张候选、新局、失焦、缓存新鲜/过期、延迟乱序、断网、429、无效响应 |

固定保留：黑暗仪式20778、应急护甲I 1023、已有强化30668、朔极之矛2004、大亨之铠6052、光明版无尽之刃2059、阵容112的阿木木4503。其余样例从真实目录按条件选择，并记录固定随机种子作可复现的补充抽样。不能只抽热门正例，也不能将合成空表算作真实空结果覆盖。

获取一份整表后，可低成本遍历所有行进行基本数值与身份检查；上表是精查范围，不是仅检查这些行。真实资料不足的格子记为 `unavailable`，保留覆盖缺口，不偷偷换成容易通过的样例。

## 数据样例、对照报告与运行入口

拟在 `outputs/companion/fixtures/data_display/` 保存精简公开响应、独立预期和来源说明；截图、完整大表等保留本地，仅引用哈希。清单至少记录：案例ID、来源页面与接口、请求维度、捕获时间、原始内容哈希、真实/合成类别、参考规则或页面证据、预期实体/数值/样本/状态/排序。

差异报告以案例为单位输出：**条件 → 来源参考 → 助手实际 → 具体差异 → 证据位置**。状态分 `pass`、`mismatch`、`source_unavailable`、`missing_fixture`、`not_run`；不把缺数据、跳过或未运行合并成通过。汇总按功能与维度覆盖，附必要界面截图，不只写“共N项通过”。

拟提供统一运行器：

- 数据快速检查：不联网、不需要MuMu、不读取私人截图；覆盖两处源码目录的相关UT和真实快照界面回归。
- 实时抽查：显式选择版本与案例批次，生成上述差异报告。
- 发版检查：前两项证据齐备后，从ZIP启动EXE回放关键样例，核对版本和包哈希。

Windows CI运行离线数据检查；真实图片/OCR独立列为扩展测试。开发机有图片而CI没有时，报告分开呈现，不能用“全部通过”掩盖跳过。

## 发布验收

1. 必选数据案例无跳过、无未解释差异；每个真实缺陷都有修复前失败的回归证据。
2. 错ID、错版本/阶段/阵容、全局冒充阵容、小样本越过排行榜门槛、数值贴错卡片、旧响应回填，均阻止标记为“数据校验通过”。
3. 用独立测试副本做少量故障注入：移除样本过滤、取错阶段、调换全局/阵容、复用旧版本缓存、互换候选槽位；测试必须分别报错，以证明它能拦截这类错误。无需引入大型变异测试框架。
4. 在线抽查存在来源不可用或资料缺失时如实报告；若仍发布测试版，必须列出未验范围，不宣称全面对账通过。
5. 不自动接受新快照覆盖旧预期。数据更新、网站规则变化和助手缺陷分别判断，确认原因后再更新基线。

本计划覆盖数据显示正确性；不承诺验证DataJ上游统计计算本身。OCR独立准确率、MuMu帧率、窗口点击穿透、安装兼容性及第三方许可补全仍是独立事项，不能用数据UT代替。此轮不改已发布的ZIP或移动版本标签。
