# 装备四选一：调研与设计方案

日期：2026-09-28。初版状态：调研与方案；用户随后已确认，实施进度见 [任务清单](装备选择实施任务-20260928.md)。真实样本补充发现成装有4/5选项，实施按实际可见数量定位；下文“四个”保留为最初设计示意，不能硬编码四格。

## 1. 目标与范围

在 MuMu 金铲铲的装备选择画面，按游戏原有顺序，在每个选项附近显示全局均排、已固定阵容的均排，以及有统计依据的装备持有者。首版覆盖普通成装、奥恩/神器装备、光明装备；散件不触发。转职、辅助装、消耗品和特殊赛季道具暂不纳入，避免把所有装备目录条目都当作成装。

默认自动检测，原有鼠标侧键作为立即查询的兜底。用户不必切换识别模式、输入四个装备名称或展开主界面。沿用助手当前选择的 DataJ 版本和固定阵容。

## 3. 建议的用户体验

### 3.1 四个选项原位对比

四块紧凑、半透明信息条分别位于对应选项上方；保留游戏从左到右的排列，不重新排序。具体位置由真实装备选择画面校准，不硬套海克斯三选一坐标。

每个选项展示以下内容（仅字段示意，不是真实统计）：

```text
装备图标  装备名称
全局  —.—   本阵容  —.—
可用持有者：英雄A —.— / 英雄B —.—
```

- 均排颜色复用 DataJ 对应口径的颜色规则；颜色之外保留明确数值和范围文字。
- 定阵后“本阵容”突出显示；未定阵时只显示全局，英雄来源标为“全局”。
- 英雄最多两个，显示头像、简称及其携带该装备时的均排。定阵后优先限定该阵容中的英雄；不足两个宁可少显示，不悄悄混入全局英雄。
- 默认对有效样本不少于 50 的持有者按均排升序展示，样本相同/均排相同时以样本量辅助排序。阈值为方案建议，不是已验证的统计保证。
- 每项自己的样本数放在紧凑次行或助手详情中；低样本明确标记。无数据、识别失败、查询失败分别显示，不能显示 0 或沿用上次数字。
- “常用英雄”和“低均排持有者”不是同一指标；若只有使用率，不冒充表现排名。均排也不表述为装备带来的因果提升。
- 版本、固定阵容名放在共用的小标题中，避免四次重复。

### 3.2 操作与退出

显示层完全鼠标穿透，不遮挡装备名称、描述和点击区域，不要求用户对准助手操作。原左上角标记仍可展开、收起；有交互的详情留在主面板中。

选择界面消失后立即清除本场结果；同一组选项稳定显示，不因每次截图而隐藏再显示。刷新/更换某项只更新对应项。切出游戏、关闭 MuMu、改版本或改阵容时立即失效旧结果。

### 3.3 自动检测与延迟

装备选择可发生在任意回合，不能仅依附 2-1、3-2、4-2。

建议初始参数：游戏在前台且助手面板收起时，每 **2 秒**采集底部小区域，用轻量场景特征判断是否出现选择界面。平时不对该区域持续运行 OCR，也不请求统计。海克斯回合探测继续使用现有 3 秒周期；两者共用调度与工作队列，避免并行抢占截图/OCR资源。

确认装备界面后才识别四项；画面无变化时复用身份和统计。选择界面存续期间用小区域检测变化/消失，初始周期 250～500ms，最终由实际 CPU、帧率和退出响应测试确定。任何时刻只允许一个重识别任务；过期任务不排队积压。

侧键无需等待 2 秒，立即按画面类型分流到海克斯或装备识别。目标是缓存命中时侧键到首屏结果 **P95 ≤1 秒**；自动检测自身另有 0～2 秒等待。首次联网和英雄明细允许异步补齐，不能承诺与缓存命中同样快。以上是验收目标，尚未实测。

## 4. 实现边界与数据合同

### 4.1 识别

新增装备选择场景，和海克斯选择、普通棋盘、商店分开。识别输入仅为本地截图：有名称时以文字及赛季目录核对，图标作辅助；只有图标时需真实游戏图标样本验证，不能假定网站图标能直接可靠匹配。

普通装备和光明版本必须映射到不同实体 ID；不靠模糊名称强制合并。每格独立保留候选、置信度和失败原因；识别不确定的格子不查数据。散件界面应由实体类型和场景证据共同排除。

尚未确认本地已有真实四选一正样本。本方案不宣称坐标、识别率或三个装备类别已经验证；批准后先盘点本地截图及已确定赛季的录像，再取得真实 MuMu 画面验证。

### 4.2 数据模型

每条结果携带：游戏/赛季、所选补丁、装备 ID、统计范围、阵容 ID（如有）、英雄 ID（如有）、均排、行样本数、来源与取数时间。

全局装备均排与阵容装备均排必须来自对应装备口径的统计；禁止简单平均各英雄均排，禁止拼接重叠样本得到假总量。三件套统计也不能当单装备统计。接口未提供的维度标记缺失。

缓存按版本、范围、阵容、英雄、装备以及实际查询条件隔离。切换版本后不得使用旧版数值；网络失败不得静默回退到其他版本。允许在数据合同支持时于后台低优先级预热全局表和固定阵容表；不在选择出现时为四项×多个英雄串行请求大量接口。

### 4.3 模块拆分建议

| 模块 | 职责 |
| --- | --- |
| 场景调度 | 共用低频探测、侧键入口、前台检查、任务取消 |
| 装备识别 | 选择格定位、类型过滤、文字/图标核验、每格身份 |
| 数据适配 | 全局、阵容、持有者的明确合同、缓存及失败状态 |
| 装备比较 | 样本筛选、排序、展示字段，不做选装自动决策 |
| 装备浮层 | 四格定位、点击穿透、稳定更新、消失清理 |
| 验证工具 | 真实图片回放、场景序列、延迟和游戏性能记录 |

仍使用现有 Python/PySide6、截图和本地识别基础；不新增第二套悬浮窗框架。现有调度依据：[app.py](companion/app.py#L840)；现有局部截图入口：[vision.py](companion/vision.py#L233)。

## 5. 批准后的实施顺序与验收

以下是阶段建议；用户确认后再细拆可执行任务并实施。

1. **先数据与样本**：冻结实际接口响应，确认三个统计范围；标注三类装备的真实选择图、散件及非选择图。若核心阵容装备统计不可得，先报告限制，不以替代数值伪装成功。
2. **先侧键闭环**：真实截图 → 四个装备 ID → 双口径均排 → 原位浮层。先解决实体与数据正确性，再加入自动探测。
3. **低开销自动触发**：合入共用调度，验证任意回合、关闭窗口、前后台切换及手动保底。
4. **持有者展示**：在可用数据合同下显示最多两位英雄，并控制请求量和缓存。
5. **自测和真实局验证**：先离线回放，再用 MuMu 标准匹配核验，不拿狂暴模式画面替代标准模式。

验收记录必须列出已测与未测内容：

- 三种装备类别各有真实正样本；散件、棋盘、商店、海克斯界面为负样本，记录样本数、逐格识别准确率、误触发与漏检，不只报成功截图。
- 训练/调参样本与最终回放样本分开；普通与光明同系列图标、动画、不同窗口尺寸、中文长名称单独覆盖。
- 同一选项持续显示不闪烁；选择结束能清除；刷新不串格；单格失败不阻断其他格。
- 无阵容、低样本、数据缺失、断网、版本/阵容切换、迟到响应均不混用统计。
- 鼠标可直接选择装备，浮层不抢焦点；侧键实际触发链路验证。
- 分别测缓存命中、首次联网和自动探测延迟；比较关闭助手、仅探测、识别瞬间的 CPU/游戏帧率及帧时间。建议稳定探测时平均帧率下降不超过 3%，超标先优化或降低频率，未经测量不宣称“不影响游戏”。
- 标准匹配中只实际遇到一种装备界面时，其余类别继续标为离线验证，不能宣称全部实战通过。

## 6. 需要确认的产品选择

建议批准：**四个选项上方各一块紧凑信息条；全局 + 本阵容均排；最多两位对应范围的持有者；任意回合每 2 秒轻量探测 + 原侧键立即查询；仅普通成装/奥恩/光明装。**

确认设计后才启动功能实施。

## 7. DataJ 本轮实测结论

完整请求、字段与局限记录在 [数据接口核验](装备四选一数据接口核验-20260928.md)。本轮请求使用 setId=18、gameVersion=18.2a；下表为当前可行性证据，不是稳定公开 API 的承诺。

| 需求 | 实测入口 | 结论 |
| --- | --- | --- |
| 全局单装备均排 | [GET /stats/equip](https://www.dataj.cc/api/web/stats/equip?setId=18&gameVersion=18.2a) | 成功；一次返回138项，可整表预热 |
| 固定阵容单装备均排 | [GET /comp/112/equips](https://www.dataj.cc/api/web/comp/112/equips?setId=18&gameVersion=18.2a) | 成功；本次68行包含普通、神器，缺光明 |
| 全局持有者 | [GET /stats/equip/2004/heroes](https://www.dataj.cc/api/web/stats/equip/2004/heroes?setId=18&gameVersion=18.2a) | 成功；含英雄 ID、均排和样本数 |
| 阵容持有者 | [GET /comp/112/equip-heroes](https://www.dataj.cc/api/web/comp/112/equip-heroes?setId=18&gameVersion=18.2a&equipId=2059) | 成功；本次光明装备也有数据 |
| 阵容表缺失的光明均排 | POST /explorer/query 单装备条件 | 已取得装备2059在阵容112的均排3.61、样本185；属于直接返回的阵容聚合结果 |

因此数据层路线是：**全局表 + 阵容表预热；阵容缺项时按实际候选装备补查检索器；持有者异步加载。** 检索器补齐的数据在详情中标明来源，样本不与其他接口混加。前两层均排不能等待全部英雄请求完成才显示。

约束：

- `recommendedHeroes` 只有身份和样本，没有英雄均排；不能用它代替持有者接口。持有者接口也未提供星级，不写成二星/三星专属表现。
- 阵容持有者响应可包含攻略默认名单之外的变阵英雄。默认浮层与当前固定阵容的英雄 ID 取交集，再排序；不按同名合并不同 ID。
- 18.1/18.2a 全局接口返回不同统计，但响应不回显版本。仅据此不能证明每个接口的全部历史版本都正确过滤；实施阶段还需按使用路径补充版本隔离验证。
- 现有适配器请求之间至少间隔1秒；首次查询四个装备的英雄数据无法保证1秒内全部完成。已缓存均排先出，补齐状态稳定显示。
- 目录白名单对应来源分类“成型装备、神器装备、光明武器”。已有目录快照的内部 season 文本与 setId 存在不一致，必须刷新并与本赛季真实装备核验，不能仅看文本标签认定赛季正确。
