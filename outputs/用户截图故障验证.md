# 用户截图故障验证 · 2026-09-27

## 确认的故障

用户提供 `MuMu-20260926-112533-073.png`，原始尺寸 3840×2160。人工先读出阶段 2-1，左至右为黑铁资产、应急护甲 I、进攻宣告。

原程序对原图返回 `scene=unknown / missing_or_ambiguous_choice_header`：它要求顶部出现选择标题，但用户截图没有该标题。失败发生在卡片识别之前。这是这张原图不工作的直接原因；不等同于还原整场运行过程。

修正选择页检测：无标题时要求三个对齐的刷新控件（含相邻次数）、明确选择阶段及对应三列标题布局。缺少刷新证据或只有标题不会按该路径接受。该布局的保鲜检测追踪回合与名称，不再追踪不存在的标题位置的动画背景。

## 修复后的实际结果

原图识别得到 2-1；黑铁资产和进攻宣告成功匹配目录。应急护甲 I 的局部 OCR 仍读为数字 1，保持未确认，不强制替换成罗马数字。

另行调用当前 DataJ 适配器成功得到所配置 18.2a、2-1 的全局统计：黑铁资产 4.28 / 972 局，进攻宣告 4.32 / 213 局。结果及获取时间保存在 `work/user-game-sample/stats.json`；这与冻结数据不同，不混为一份结果，也不能保证补丁口径与截图对局一致。

## 关闭后继续修复

遵照用户“修好了再开”，未启动助手。通过隐藏窗口的确定性回归复现并修正两项结果生命周期问题：

1. 同一组选项每次 OCR 完成都重新创建会话版本，使仍在等待的统计响应失效。现在同一组选项复用进行中的请求及已确认结果；刷新、换阶段、失焦等失效规则保留。
2. 截图前隐藏浮层后，若达到 OCR 间隔但识别线程仍忙，原分支只尝试再次启动 OCR，不恢复已有浮层。现在画面仍有效时独立恢复结果显示。

`check_result_stability.py` 先失败后通过。`check_user_refresh.py` 使用用户两张真实 2-1 原图与随后棋盘图验证：刷新后旧响应丢弃、白银命运保持缺数据、离开选择页清空结果。24 项单元、9 项数据界面、9 项简化流程回归通过。实时画面反复变成 unknown 的具体像素证据仍缺失，不能把这些修正等同于完整实战修复，因此继续保持助手关闭。

## 4-2 诊断帧与性能修正

后续保留的 `frame-2.png` 是真实 4-2 选择页，原始拒绝原因终于可复现：中间禁用刷新按钮的 C / 0 检测框重叠约 12 像素，原配对规则要求零重叠，整页因此被拒。现在容许有限的检测框重叠，同时保留相对方向、同行、唯一计数配对和三列布局检查。回归先失败后通过；完整 OCR 可确认贸易中心、男爵幻域、1个霸符，2个霸符。原始证据已复制到 `work/user-game-sample/live-failure/`，不会被诊断循环覆盖。

日志证实原实现即使在普通棋盘也连续执行约 3 秒的全图 OCR。改为轻量刷新箭头图形预筛（只决定是否启动 OCR，不决定名称或数据）；普通棋盘跳过模型推理。同一组选项没有变化时复用结果；识别结束后留出休息间隔；无选择状态截图间隔改为 1 秒。默认关闭原图诊断写盘，只有显式设置 `DATAJ_DIAGNOSTIC_FRAMES=1` 才启用，轻量流程日志保留。

离线同一普通战斗图预筛约 20–22 ms、CPU 约 16 ms，原日志约 3.6 s OCR；这是识别处理耗时，不是游戏 FPS 测量。16 秒固定 4-2 图流程仅运行一次完整 OCR，后续维持结果；19 次模拟截图、45 次浮层放置调用，初次结果约 5.31 s（包含冷启动），CPU 累计 9.42 s。显示使用冻结数据，不是当前实时统计；真实截屏成本及游戏帧率仍未计入。未重启助手。
