## 已观察的数据入口

下表路径前缀均为 `https://www.dataj.cc/api/web`。HTTP 方法和参数来自前端实际调用，尚未在本次子任务请求接口。

| 功能 | 方法与路径 | 前端实际传入 |
|---|---|---|
| 全局海克斯统计 | GET `/stats/hex` | `setId, gameVersion` |
| 阵容详情 | GET `/comp/{compId}` | `setId, gameVersion` |
| 阵容海克斯完整统计 | GET `/comp/{compId}/hexes` | `setId, gameVersion` |
| 阵容推荐海克斯 | GET `/comp/{compId}/recommended-hexes` | `setId, gameVersion` |
| 阵容英雄统计 | GET `/comp/{compId}/heroes` | `setId, gameVersion` |
| 阵容下指定英雄出装 | GET `/comp/{compId}/hero-equips` | `setId, gameVersion, heroId` |
| 阵容装备统计 | GET `/comp/{compId}/equips` | `setId, gameVersion` |
| 阵容下指定装备携带者 | GET `/comp/{compId}/equip-heroes` | `setId, gameVersion, equipId` |
| Explorer 检索 | POST `/explorer/query` | JSON `{setId, version, filter}`；注意这里叫 `version`，不是 `gameVersion` |
| 游戏实体字典 | GET `/gamedata` | `setId`，源码转成字符串 |
| 游戏版本目录 | GET `/gamedata/gameVersion` | query 原样传递；本次不推定未读到的参数 |

准确定位片段：`request.get("/stats/hex",{query:e})`；``request.get(`/comp/${r}/hexes`,{query:n})``；`getCompHeroEquips)({compId:ex,setId:ew,gameVersion:ej,heroId:e1})`；`e={setId:_,version:T,filter:c},n.request.post("/explorer/query",e)`。

请求封装对所有非 null query 值执行 `String(t)`，JSON body 设置 `Content-Type: application/json`。若响应是包含 `data` 的对象，则客户端解包成 `{ok:true,data,...}`；否则直接把响应当 data。**客户端的 `ok` 是封装结果，不能推定服务端也有 `ok` 字段。** 当前封装允许但未强制指定 credentials，没有发现这些调用额外传 token；这也不能证明接口长期无需登录或可以任意频率使用。

## 海克斯阶段：最容易发生的统计错误

公开前端明确映射：`0 → 2-1`、`1 → 3-2`、`2 → 4-2`。这是强化符文槽位索引，不是游戏大阶段数。源码片段为 `[{value:"0",label:"2-1"},{value:"1",label:"3-2"},{value:"2",label:"4-2"}]`。

`getHexStats` 只按赛季、版本请求。名称、品质、阶段以及“区分阶段”均在客户端筛选。`buildHexStatsDisplayRows(rows, splitRound, selectedRounds)` 的实际行为：

1. `splitRound=false` 且未选择阶段：展示海克斯整体行的统计。
2. `splitRound=false` 且恰好选择一个阶段：用该 `roundStats` 条目的 `sampleCount/playRate/avgPlacement/top4Rate/topRate` 覆盖整体统计。
3. `splitRound=false` 且选择多个阶段：筛掉完全没有对应阶段样本的海克斯、调整阶段标签；**仍保留整体统计值，没有对已选阶段重新计算合并均排。**
4. `splitRound=true`：每个 `sampleCount>0` 且命中筛选的 `roundStats` 单独成为一行；键为 `${hexId}-${round}`。
5. 阶段级 `placementDelta` 缺失时源码退回整体值；阵容页对带 round 的行不显示整体 tier。Companion 不应把整体名次差或评级误标为该阶段独立指标。

阵容页使用同一转换函数。另一个细节：阵容海克斯最小样本（默认 50）是在拆阶段之前按整体 `sampleCount` 过滤。因此网页拆出来的某阶段可以低于 50 个样本。Companion 若显示小样本提醒，应按实际阶段条目检查，而不是以为页面默认阈值保证每阶段都达标。

## 阵容、英雄、装备字段

`/comp/112` HTML 的初始阵容是“地狱火95”，同为 `setId=18, gameVersion=18.2a`。HTML 已交付 `initialComp, initialHeroes, initialRecommendedHexes, initialBattleBuilds`；没有把完整海克斯均排表或英雄出装表作为这几个初始属性交付。

`initialComp` 含 `compId,name,gameCode,heroes,traits,equips,top4Rate,topRate,pickRate,avgPlacement,sampleCount,tier,dataMode`。当前样本 `dataMode="stats"`。`gameCode` 是带“阵容码”前缀的完整字符串，不能只复制内部编码而假定格式等价。

必须区分 **阵容英雄记录 ID 与游戏英雄 ID**。例如希维尔的阵容记录 `id="2288"`，但 `heroId="4510"`；阿木木分别为 `2289`、`4503`。出装请求使用 `heroId`，不能把 UI 选中记录 ID 直接传过去。阵容装备关系还含 `compHeroId`，可以定位同英雄多记录情形。

源码消费的响应结构：

- `/hexes`：`data.hexes`，行含 `hexId, sampleCount, playRate, avgPlacement, top4Rate, topRate, placementDelta, tier, rounds, roundStats`；具体可选字段仍需动态样本验证。
- `/hero-equips`：`data.heroEquips` 与 `data.hero3Equips`；行用 `equips[]`、`sampleCount`、统计列；过滤按装备目录 `type`、名字和最小样本执行。英雄 API 返回整体英雄出装，UI 在本地切换单件与三件装。
- `/equips`：`data.equips`，可见 `equipId,type,playRate,avgPlacement`；选中后请求 `/equip-heroes`，消费 `data.heroes`。
- `initialHeroes`：`id,heroId,heroName,price` 以及统计字段，另有 `starBreakdown`、`equipCountBreakdown`。
- **`initialRecommendedHexes` 不是海克斯均排**：样本里只有 `hexes[].id/name/pickRate/pickCount`；不能拿推荐列表代替 `/hexes` 的阶段统计。

## Explorer：实际条件结构

前端根节点强制 `combinator:"and"`；分组可为 `and/or`，前端常量 `MAX_FILTER_GROUP_DEPTH=3`。规则字段来自 `createEmptyCompFilterRule` 与新增条目逻辑：

```json
{
  "setId": 18,
  "version": "18.2a",
  "filter": {
    "combinator": "and",
    "rules": [{
      "type": "hex",
      "targetId": "30668",
      "targetName": "厨神阿福",
      "starCount": "",
      "equipCount": "",
      "hexRound": "1",
      "equipCarry": "",
      "nameMatch": false,
      "enable": true,
      "exclude": false
    }]
  }
}
```

这个结构是从正常 UI 调用拼接得出的**待验证请求样例**，本次未发送；`hexRound="1"` 对应 3-2。type 候选为 `hero,trait,equip,hex`；羁绊另有可选 `traitLevel`，可用实体 ID 应来自页面已有目录，不枚举猜测。无条件时传 `filter:null`。

源码读取结果的 `overview,comps,heroes,traits,equips,hexes,heroEquips,hero2Equips,hero3Equips`；`overview` 使用 `battleCount,avgPlacement,top4Rate,topRate`。表格行消费 `id,heroId,heroName,equips[],sampleCount,playRate,avgPlacement,placementDelta,top4Rate,topRate` 等，未证明每一种结果都有全部字段。

结果内名字、装备类型、海克斯品质、英雄费用、最小样本等是客户端过滤，默认最小样本 50；不能把这些 UI 控件直接当作请求参数。当存在启用且非排除的英雄或装备条件时，“装备”标签改用 `heroEquips` 数据，否则用 `equips`。这会改变“装备统计”的上下文，适配层必须显式保留 scope。

## 主任务的有限动态验证

主任务已对 `/api/web/stats/hex?setId=18&gameVersion=18.2a`、`/api/web/comp/112/hexes?setId=18&gameVersion=18.2a`、`/api/web/comp/112/hero-equips?setId=18&gameVersion=18.2a&heroId=4503` 各请求一次，记录 HTTP 200。本文作者随后读取保存的 JSON，确认服务端真实外层是 `code,success,message,data`，其中 `code=200,success=true`，与客户端封装的 `ok` 不同。

证据文件位于 `work/dataj-p0/global-hex.json`、`comp112-hex.json`、`comp112-amumu-items.json`。

这些是固定版本快照验证，不证明生产 SLA、授权或未来兼容性。Explorer、装备目录等是否已经验证，以主任务后续 P0 验证记录为准。

### 地狱火纹章单条件的结构与后续验证

三个 HTML 的 `hydration` 只有赛季/版本目录，没有完整装备字典。地狱火纹章 ID 应来自前端明确加载的 `/api/web/gamedata?setId=18` 返回 `data.equip`，按 `name` 对齐；不要猜测 ID。取得 ID 后沿用上面的 Explorer 样例，把 `type` 改为 `equip`、`targetId` 改为字典 ID、`targetName` 改为地狱火纹章、`hexRound` 改为空字符串，其他字段不变。正常 UI 新增规则没有要求额外生成规则 ID。

主任务后续补充：实体目录返回地狱火纹章 ID `41806`，HTTP 200；按上述结构发起一次 Explorer 查询，HTTP 201、业务 code 200、success true。概览 n=44073、均排3.84；地狱火95条件内 n=34791、均排3.70，与网页一致。目录元数据差异和完整请求体见 [P0 验证记录](P0验证记录.md)。本文其他尚未发送的入口仍仅属于源码发现。

## 给实现的约束

- 全局/阵容海克斯按 `setId + gameVersion + compId?` 缓存原始整表，局内按已识别槽位直接选 `roundStats`；不为每个候选海克斯重复发请求。
- 局内只查询一个明确阶段，不沿用网站多阶段未拆分的混合显示方式。
- 推荐列表、攻略推荐装备、原始统计三者分别建模；缺失均排不能从 pickRate 或推荐顺序估算。
- 把第三方未公开承诺的路由放在独立适配器；字段缺失、赛季变化和返回错误需可回退到原网页。
- 核心四类入口均已由主任务完成典型请求。后续补充少量边界样例和元数据验证，不需要扫描全站；不能以典型请求成功代替完整验收。
